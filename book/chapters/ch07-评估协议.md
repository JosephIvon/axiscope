## 7.1 概念：评测是最容易自欺的一环

一个诊断引擎**总能**在自己的测试集上表现不错——
只要测试集是照着引擎的毛病设计的。

C5 的标题就写着它要防什么（`docs/contracts/C5-evaluation-protocol.md:1`）：
**C5 评测协议（防自我验证）**。

§0 讲的是"要解决的问题"（`docs/contracts/C5-evaluation-protocol.md:3`），
而解药就是 A-88（同源无证明力）。把这条单独拎出来看：

> **凡由某个知识库/契约/代码派生的核对物，对其自身来源的证明力记 0。**

这条纪律的应用面极广：

- 用本仓的 KB 写的测试题 ⟹ 不能证明本仓的引擎准；
- 用本仓的契约写的断言 ⟹ 不能证明契约对；
- 用引擎自己的输出当"期望值" ⟹ 不能证明任何事。

**它的直接推论是**：想证明自己准，就必须去找**仓外**的东西——
公开数据集、厂商手册、第三方工件。第 4 章讲的 `external_reference`
（`docs/kb/KB0-conventions.md:72`）与 A-88 是同一件事的两面。

## 7.2 五档证据与两层指标

C5 §1 是证据分层（`docs/contracts/C5-evaluation-protocol.md:19`），
tier 的值域是五档（`docs/contracts/C5-evaluation-protocol.md:25-31`）：
T1-a / T1-b / T1-c / T2 / T3。

其中 T1-a 是 DaRUS（斯图加特大学，CC BY 4.0，32/40 通道，
fs = 1 kHz ⟹ 奈奎斯特 500 Hz ⟹ `reliable_band_hz = 400`）
（`docs/contracts/C5-evaluation-protocol.md:25-31`）；
T1-b 是 CWRU/帕德博恩/Aalto/MFPT，**只计二分类、禁映射 slug**（同段）。

**指标必须按层分别报告，禁止合并成一个总数**
（`docs/contracts/C5-evaluation-protocol.md:21-22`）。

以及那条最要紧的分层规则
（`docs/contracts/C5-evaluation-protocol.md:37-42`）：

- 对外能力性指标**只能**来自 T1+T2；
- T3 指标只出现在"流程正确性"章节，标题须写明
  「**合成集，不用于能力主张**」；
- T1-c 禁与 T1-a/T1-b 混算；拿不到工装则**整层撤回**。

**"拿不到就整层撤回"**比"拿不到就少报一点"强得多。
它意味着：某层数据不可用时，**不允许用别的层的数字来顶**。

## 7.3 冻结与切分：60/40

C5 §2 是冻结与切分（`docs/contracts/C5-evaluation-protocol.md:44`）：

- 开发/隐藏测试集 **60/40**（`docs/contracts/C5-evaluation-protocol.md:46-47`）；
- 隐藏集冻结哈希 `bench/hidden.sha256`；
- **调提示词、调阈值、挑模型，一律不得看它**；
- 冻结后**禁止**针对失败案例改规则。

最后一条是重点。"看到失败案例就改规则去修它"是评测失效的头号原因：
改完之后，隐藏集就不再是隐藏的了。

冻结机制在 KB8 里有具体实现
（`docs/kb/KB8-benchmark-cases.md:149-152`）：

```
digest = SHA256( bytes(meta.json) || 0x00 || bytes(waveform.tsv) || 0x00
                  || bytes(events.jsonl 若有，否则空) )
```

三段固定顺序、`0x00` 分隔；**缺 events 时用空段**——
这样"无事件孪生"与"有事件孪生"必然是两个不同摘要。
冻结后写入 `bench/hidden.sha256`；**追加任一案例 ⟹ 全量重划 + 版本号 +1**
（`docs/kb/KB8-benchmark-cases.md:152`）。

KB8 还有一条关于"案例身份"的根本规定
（`docs/kb/KB8-benchmark-cases.md:144-146`）：

> 案例身份由"**喂的是什么数据**"定义，
> **不由"我们的管线在它上面看到什么"定义** —— 身份随管线变等于允许看着管线输出挑案例。

这句话把"数据泄漏"这个抽象概念，落成了一条可执行的规矩。

`docs/contracts/C5-evaluation-protocol.md:72-84` 的指标：

|---|---|
| Top-1 | ≥ 45% |

| 证据准确率 | 100% |
| 无依据成功声明 | **0 次** |

| 建议有效性偏差 | ≤ 30% |

其中"分母仅 T1-a + T2，T1-b 不进"（`docs/contracts/C5-evaluation-protocol.md:72`）。

### 7.4.1 证据准确率 100%：结构上无法造假

C5 §3 有一条很硬的规定
（`docs/contracts/C5-evaluation-protocol.md:86-88`）：

> 规则引擎只能引用 C2 特征路径、不允许自带数值；
> 加载期校验每条证据 `feature` 可解析且 `value` 一致，不一致直接抛异常 ⟹
> 证据准确率"**结构上无法造假**"。

**"结构上无法造假"**是本仓评价体系里最高的赞美。
它的实现方式是：证据里的 `feature` 路径与 `value` 不是引擎自己写的，
而是**加载期对着 C2 产物逐条核对**的——
路径不存在、值对不上，**抛异常**，不进入后续流程。

这和第 2 章"落码侧与复算侧不得各自发明"
（`src/axiscope/core_hash.py:3-5`）是同一种思路：
**不是靠检查，是靠结构让造假不成立**。

### 7.4.2 难度与"正确答案是拒绝下结论"

C5 §2 规定 difficulty 必须包含缺通道、缺定标系数、多故障叠加，
以及 **`none_of_the_above`（正确答案是拒绝下结论）**，
最后一类**占 ≥ 15%**
（`docs/contracts/C5-evaluation-protocol.md:65-66`）。

KB5 那边给的是同一件事的另一面
（`docs/kb/KB5-simulation-plant.md:1300-1301`）：
`none_of_the_above` 占 **≥15%**，目标 15–20%。

**为什么必须有一批"应该拒答"的题**：
一个总是给答案的系统，拒答正确率是 0；
一个总是拒答的系统，拒答正确率是 100% 但毫无用处。
只有把这两类放在同一个评测集里，**拒答正确率**才是一个有意义的指标。

C5 §7 还写明：**未发现异常**类措辞在 `blocked_rules` 非空的案例上出现 ⟹
命中禁语违例（**0 次硬门禁**）
（`docs/contracts/C5-evaluation-protocol.md:155-166`）。

而"真空能力项"的合法输出是 `not_evaluable` 登记 + 拒答，
**计入拒答正确率分母、不计入任何命中率分母**（同段）。

## 7.5 本仓当前的基线：0 与 null

现在看实际数字。评测产物在 `build/c5-eval/`
（`metrics.json`、`per_case.json`、`diagnoses/` 7 份）
（`docs/wiki/07-run-guide.md:56`）。

**当前指标基线**（`docs/wiki/07-run-guide.md:56`）：
dev 4 + T1-a 7 例，**`top1_hit = 0`、`ece = null`**、严格拒答 7/7。

**样本量远低于 KB8 下限 120，任何准确率声明都无分母**（同句）。

`bench/` 的规模（`docs/wiki/05-toolchain.md:10-16`）：

- 共 **7 条**（dev 4 / hidden 3）；
- 期望类分布：`refuse_insufficient_data` 4 / `co_occurrence_only` 2 / `none_of_the_above` 1；
- 真值只来自 INJ-01/04/11/15/19，**唯一非同源真值是 CTL-0001**；
- `bench/forbidden_patterns.json` 6 个 token：`kHz_absent` / `no_anomaly_claim` /
  `field_effective` / `thermal_drift` / `sub_quantum_mm_claim` / `simulation_validated_claim`；
- `run_eval` 的指标键名（`docs/wiki/05-toolchain.md:16`）：
  `top1_hit` / `top3_hit` / `in_hit_denominator` / `refusal_correct` /
  `refusal_correct_strict` / `ece`（10 桶）/ `evidence_rows_checked` /
  `evidence_rows_bad` / `forbidden_hits` / `unsupported_success_claims` /
  `expected_blocked_by_covered` / `band_gate_r03_r04_blocked` /
  `contract_checks_total` / `failed` / `traceable`。

**请把这屏数字读三遍**：

1. `top1_hit = 0` —— **一条都没对**。
2. `ece = null` —— **不是 0，是不给数**（分母为零）。
3. 严格拒答 **7/7** —— **拒答全对**。

这三条放在一起才是完整的一句话：
**在这 7 个样本上，引擎正确地什么都没说。**

而 `top1_hit = 0` 里，4 个样本的期望类本就是 `refuse_insufficient_data`——
**拒对了**；2 个是 `co_occurrence_only`；1 个是 `none_of_the_above`。
所以"Top-1 命中 0"在这批样本上**不是引擎差**，是
**这批样本全都不该给 Top-1 命中**。

这正是 C5 的设计意图：**评测集里大部分是"应该拒答"的题**。
一个在这些题上 Top-1 很高的引擎，反而是**该被怀疑**的。

## 7.6 规模下限与配额：N = 120

KB8 §6 是规模与配额建议（`docs/kb/KB8-benchmark-cases.md:419`）：

- **建议总规模 `N = 120`：dev = 72，hidden = 48**
  （`docs/kb/KB8-benchmark-cases.md:425`）；
- 机械/电气正例 ≥ 26（13 slug × 2）；
- 软件族纪律例 ≥ 7；
- 孪生另两态补 **7×2 = 14**（全族 7×3 = **21**）；
- `none_of_the_above` ≥ 18（≥ 15%）；
- 过频带 ≥ 3；仅有波形无事件上下文 ≥ 4；
- `counts_per_mm = null` ≥ 3；`sensor_config = unknown` ≥ 2；
- 混淆/叠加专项 ≥ 8；热型两 slug 拒答专项 ≥ 2；
- KB6 门禁三例 ≥ 3；约定/接线真值缺失专项 ≥ 4（拒答形）+ ≥ 2（③a/③b 分档形）。

**能力配额下限**（`docs/kb/KB8-benchmark-cases.md:449-454`）：
软件族能力配额 = **0**；热型两 slug 的 slug 级能力配额 = **0**；
T1-b 案例整体只进 family 级分母、不占 slug 级配额。

**"软件族能力配额 = 0"** 是覆盖矩阵里的空格
（`docs/kb/KB8-benchmark-cases.md:264-267`）——
软件诱导族整行 T1-a/T1-b 都是 `—`：
**差异化能力（软件族）没有外部真值**。

而 KB8 的图例里 `—` 的含义被特别解释过
（`docs/kb/KB8-benchmark-cases.md:229-232`）：
**空格是裁决结果，不是待闭合缺口**。

**这是本仓文档里最诚实的一个排版决定**。
一张覆盖矩阵里，最容易被读者读成"还没做完"的那几格，
被明确标注为"**这里本来就不该有**"。

## 7.7 止损条件与结构性真空

### 7.7.1 止损

C5 §7 写了止损条件（`docs/contracts/C5-evaluation-protocol.md:125-131`）：

- **W+3 天**拿不到 ≥ 2 份真实厂商示波器 CSV ⟹
  报告首页明示"**全部为合成与公开数据集，无厂商真机波形**"；
- **W+7 天** T3 端到端跑通 + T1 上分出 CWRU 3 类故障；
- **W+14 天** T1-a + T2 Top-3 ≥ 60% 且 ECE ≤ 0.15。

止损条件是**带日期的**。它把"再等等"变成"到 X 天为止"。

### 7.7.2 结构性真空

C5 §9 是"结构性真空与拒答纪律"
（`docs/contracts/C5-evaluation-protocol.md:142-166`）。

**结构性真空**指：某些能力**在现有公开数据上根本不可达**。
C5 举了两个具体例子
（`docs/contracts/C5-evaluation-protocol.md:152-153`）：

- `mechanical_thermal_drift` / `electrical_motor_heating`；
- R-03/R-04（机械谐振·双惯量配对与电流环带宽类）：
  因 T1-a 数据层面不可达（需 `reliable_band ≥ 2000 Hz` 而实际 400 Hz）。

处置方式写得很死（`docs/contracts/C5-evaluation-protocol.md:152-153`）：
报告侧 `unavailable` + `freq_limits.blocked_rules = ["R-03","R-04"]`，
**禁止**输出"未发现异常/未发现谐振/无共振风险"。

这就把第 3 章那条"看不见 ≠ 没有"从**单条规则**升级成了
**一个章节级别的能力声明纪律**。

## 7.8 人工基线：一个还没付的账

C5 §5 是人工基线（`docs/contracts/C5-evaluation-protocol.md:107`）：
需要 **≥ 2 位做过伺服调试的工程师**。

而当找不到 2 位工程师时
（`docs/contracts/C5-evaluation-protocol.md:113-114`）：

> 只报 agent 自身指标并写明"**无人工基线，绝对数值不可横向比较**"，
> 不允许用文献他人系统数字当基线。

"用文献里别人的系统数字当基线"是极常见的做法，也是**最没有意义的**：
那些数字来自不同的硬件、不同的数据、不同的指标定义。

KB8 §5 也标着"**尚未完成**"（`docs/kb/KB8-benchmark-cases.md:375`），
并把人工基线称为"**最贵的一步**"。

还有一条协议细节（`docs/kb/KB8-benchmark-cases.md:410-414`）：
人工标注只允许"22 slug 内的根因排序 + 置信度 + `none_of_the_above` 判定"，
**不允许自由文本命根因**；分歧由第三人裁决，不可调和者退集标 ambiguous；
**人标与 agent 结果都只算 T1+T2 层，绝不与 T3 混算**。

最后那条是红线 4——**人也不能拿合成集当基准**。

## 7.9 动手：跑一次评测，读懂 null

```powershell
cd /d/workspace/axiscope
PYTHONPATH=src PYTHONIOENCODING=utf-8 python bench/run_eval.py > build/c5-eval/run.log 2>&1
```

然后读 `build/c5-eval/metrics.json`，逐个确认：
`top1_hit` 是多少、`ece` 是不是 `null`、`refusal_correct_strict` 是多少、
`forbidden_hits` 是不是 0。

**再确认一件更要紧的事**：
`bench/hidden.sha256` 存在吗？`bench/cases.jsonl` 里有几条？
（`docs/wiki/05-toolchain.md:12-14`）

**然后做一次自欺实验**（这一步是重点）：
在 `bench/cases.jsonl` 里挑一条**期望类为 `refuse_insufficient_data`** 的案例，
把它的 `expected_verdict_class` 改成一个"应该命中"的类，
重跑评测，看 `top1_hit` 会不会变。

它**不会**变——因为引擎是拒答的，改期望值改不了引擎的行为。
**但它会变你的报告**。这就是"挑案例"的入口。

**动手验收**：你能说出 `ece = null` 与 `ece = 0` 的区别，
以及为什么前者更诚实。
