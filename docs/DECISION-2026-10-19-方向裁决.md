# 决策纪要 — 三方向冲突裁决（2026-10-19）

输入：自研四路调研 + 外部三份草案（下称 A 四方案 / B 泛列 / C EquipPilot 立项书）。

## 1. 三份草案的共同点（全部吸收为设计约束）

| 共识 | 来源 | 落点 |
|---|---|---|
| 绝不让 agent 直接下发参数到真机 | A 的"可审核可追溯"、C 的"安全边界" | C3 `safety.writes_to_device=false`、`requires_human_approval=true` |
| 每条结论必须带来源与置信度 | A、C | C3 证据结构 + C5 ECE 指标 |
| 用客观验证取代"模型评判模型" | C 最强的一条 | C4 验证门控 + C5 三层证据 |
| 先冻结契约与评测集，再写 agent | C 结尾 | 当前阶段（P0/P1）不做任何 agent 代码 |
| 必须有明确止损条件 | C | C5 §7 |

## 2. 核心冲突：草案 A 断言"伺服整定 AI 碰不了"

**裁决：该断言错误，混淆了两件事。**

- **在线闭环自整定**（无人参与、实时改驱动器参数、带负载）——确实不能碰。安全与责任问题，不是能力问题。
- **离线诊断与参数建议**（从已录制波形出报告）——是纯数据分析。
  "没有闭环反馈"这个前提是错的：**录下来的波形就是闭环反馈的完整记录**。

证据：
1. 厂商自己就在做离线波形分析——安川 SigmaWin+、松下 PANATERM、三菱 MR Configurator2、
   汇川 InoServPad、倍福 TE5960 自整定 + Bode Plot 测量。
2. 调研确认的空白恰恰是：**没有一家做跨品牌波形归一化 + 可解释根因归因 + 仿真验证后再输出**。
   大厂 agent（西门子 Eigen、倍福 CoAgent、CODESYS AI）全部停在"生成代码"。
3. 草案 A 的"AI 碰不了"清单（插补、EtherCAT 实时配置、飞拍时序、现场偶发偏差定位）
   实际只覆盖 JD 的实时执行与安全功能，约占该岗位工作量 15%。
   其余 85% 是架构、适配、工艺实现、数据分析、文档、排障——AI 都能碰。

**吸收 A 的合理部分**：A 把"整定"理解为"在线自动调"，这个担忧真实存在。
应对：C3 明确本项目交付物是**建议 + 仿真验证 + 现场操作步骤 + 风险与回退方法**，
不含任何自动写入；`field_procedure` 字段就是为"人去执行"设计的。

## 3. 对草案 A 四个方案的评价

| 方案 | 判断 | 理由 |
|---|---|---|
| 一 SDK 适配知识库+代码骨架 | 有效但差异化弱，列为**备选**（C5 §8） | 冷启动成本分析正确（SDK 文档本身已数字化）；"骨架而非完整实现"是对的幻觉抑制策略。但 GitHub 已有 222★ 固高/雷赛二次封装、`MotionCalibrationStudio`（抽象层+九点标定+仿真卡）、CSDN《一套代码玩转多家控制卡》，正运动官方在推自家跨卡统一 API。抽象层本身不新，只剩"差异矩阵+换卡影响报告"有价值。且该方案是 LLM 应用工程（RAG+代码生成），**不展示算法深度**，对"AI 算法工程师"定位信号不准。 |
| 二 文档/规范生成器 | 最弱，不做 | 纯提示工程，零壁垒。但"必须先有团队模板库与 ADR 库，否则等于凭空写文档"这条批评有效——同样适用于我们：C5 的 T2 层要求规则阈值必须取自文献而非自造。 |
| 三 多源日志时间线关联 | 真痛点，但**自我验证循环比我们的 T3 更严重** | "找时间戳差几毫秒"确实是 senior 的时间黑洞。但公开的多源工业故障日志语料**几乎为零**（上位机日志+PLC 日志+pcap+EtherCAT 诊断同案例的公开语料不存在），意味着要自己造故障、自己写日志、自己定正确答案。C 批评的"数据自己编、答案自己编"在这个方案上无处可逃，且没有 CWRU 这种外部锚点可退。 |
| 四 工艺参数知识库 | 不可演示，不做 | 没有任何公司会公开历史 Recipe 与良率数据。前置"知识审计"成本极高。 |

## 4. 对草案 B 的评价

整体是头脑风暴，未划边界、未评数据可得性、未给形态与验收标准，12 个 agent 里多数是
"代码审查/测试生成/接口文档/技术方案/协作沟通"——这些是任何公司都有 Copilot 的通用能力，
且完全没碰 JD 的核心（运动控制卡品牌差异、伺服波形、多轴联动）。**不作为选题依据。**

**唯一采纳的洞见（这是 B 全部价值）**：故障归因要做**三方归因——机械 / 电气 / 软件**。
其中**软件侧原因**（上位机线程调度抖动、插补缓冲欠载、通信周期丢包、GC 停顿）
只有上位机工程师会想到，而伺服厂商工具完全看不到这一层。
→ 已写入 C2 特征：`tracking.corr_fe_vs_jerk`、`quality.dt_jitter_ratio`、`io` 位解码；
→ 需在 KB3/KB4 中补一条独立判据族：`software_induced_error`，
   与 `mechanical_*` / `electrical_*` 并列。这是差异化点，不是补充项。

## 5. 对草案 C（EquipPilot）的评价

**方法论最强，方向最偏。**

采纳（已整体吸收为 C5）：
- 三层数据集分离，且**指标按证据层分别报告、禁止合并成单一总数**
- 隐藏测试集 + 开发/测试分离 + 冻结哈希
- 消融实验 A/B/C/D 与"若自主循环无改善就砍掉"的自否原则
- 失败案例公开 + 混淆矩阵
- "无依据成功声明 = 0 次"作为硬门禁
- 先冻结基座与评测方案再写 agent
- 止损条件表

拒绝其方向，理由三条：
1. **定位漂移**：它把项目从"工业运动控制领域 agent"改成"无领域的 SWE-agent"。
   输入是"可复现的软件缺陷"，输出是"补丁通过测试"——这是通用编码 agent，
   正面对上所有 AI 实验室已发表的 SWE-bench 系工作，赛道拥挤且我们不占优。
2. **与目标错位**：用户是 AI 算法工程师，目标岗位 JD 的核心考察是
   "读懂伺服波形""跨卡差异""多轴联动调试"。一个 C# 修 bug 的 agent
   **不证明任何一条**。它把领域知识降级为"测试床"，而领域知识恰恰是我们唯一不可被替代的资产。
3. **它批评的循环论证，它自己更严重**：它说"数据集自己编、答案自己编、大模型打分"是假象。
   但路线 A 是"自己写模拟器 + 自己植入缺陷 + 自己写隐藏测试"，闭环完全自造；
   而我们的路线有 **CWRU / 帕德博恩这类外部真值数据集**、
   有**文献公式与厂商手册阈值**、有**物理模型**作为外部锚点。
   它的 §四"第三层：NASA 轴承与丝杠数据"其实正是我们的主数据源，却被它降级为辅助。

保留其诚实性要求：C 明确写了"40% 成功率若任务集过简单则无意义，需报难度分层与人工基线"。
→ 已写入 C5 §2（difficulty 字段、`none_of_the_above` 案例 ≥15%）与 §5（人工基线必做）。

## 6. 裁决后的最终方向

**主作品（唯一）：运动轴/伺服波形离线诊断智能体**
- 内核：跨品牌波形归一化（C1）→ 确定性特征（C2）→ 规则库三方归因（C3，含机械/电气/**软件**三类）
  → 仿真验证门控（C4）→ 可审核诊断报告
- 外壳叙事：锚定耦合设备寻光/峰值锁定失败与贴片机取放节拍（JD 第 7、5 条），提供痛点真实度
- 子模块：九点/手眼标定残差诊断（纯几何、零硬件、可作快速产出的第二证据）
- 评测：C5 全套，T1 用 CWRU/帕德博恩，T2 用文献阈值，T3 只做流程回归
- 明确不做：在线整定、自动下发、多智能体、微调模型

**已放弃**：适配层（降为 C5 §8 止损备选）、文档生成、工艺知识库、通用代码修复 agent。

## 7. 当前唯一的外部依赖（阻塞项，非代码）

C5 §7 的 W+3 天判据需要**至少 2 份真实厂商示波器导出 CSV**。
这是整个项目可信度链条上唯一无法由我们自己造的一环。
→ 待办：向有伺服驱动器与调谐软件的朋友/前同事索取脱敏导出文件；
   或向汇川/固技术支持工单索取样例；或用厂商手册中的格式规范写一个"合规合成导出器"并如实标注。
