# AUDIT — 第三家（GLM 系）「上位机代码工厂」核查与裁决

日期：2026-10-20　核查方式：**验证性执行**（真实调用 `csc.exe` 重编译、真实运行产物、逐行读生成代码），
不是读它的交付说明。对象目录：`<Trae-CN 会话临时目录>\`
（主交付 `上位机代码工厂.html` 165 KB 单文件 + `gen/` 生成引擎 2857 行 + `out/` 各品牌样例包）

## 一、它做了什么

同一份 JD（半导体封装设备运动控制上位机高级工程师）下的第三种切入：
不做诊断，做**代码工厂**——输入品牌/轴数/功能开关，输出可编译的 C# 分层工程：
`IMotionController` 抽象层 + 固高/雷赛/正运动/ACS/软赢/高川 品牌适配器（P/Invoke）+
虚拟控制器 + Modbus 驱动生成 + 品牌能力差异矩阵 + API 核对清单。
命中 JD 职责 #2（分层架构）+ #3（适配层，"换卡不改业务代码"）+ #8（协议与 SPC）。

## 三、致命结构问题：核对清单兜不住函数名

各 SDK 的函数签名是**凭记忆**生成的（它的思考过程自己承认"实际记不准"）。抽查结果：

- `ZAux_Direct_GetIdle / Cancel / GetAd / Servo`：明显拼凑，真实名疑为 `GetIfIdle` / `Single_Cancel` / `GetAdc`，`Servo` 不存在；
- `GT_GetSts(out int, short, out uint)`：官方 `pSts` 疑为 `short*`，4/2 字节错位在现场是**栈损坏**级别；
- `GT_SetTrapPara` 结构体字段序疑错（`smoothTime` 类型也错）；
- `dmc_set_profile` 7 参形式型号相关。

而 `ApiChecklist.md` 是**照着生成的代码自身**生成的（`ZAux_Direct_GetIdle` 在清单里原样复述）。
所以"0.5–1 天按核对清单确认"这句话不成立：清单里没有独立信息源，它只能提醒你"这里要核对"，
无法告诉你"哪里错了"。这是**自验证循环的第二个实例**——和 minimax 那套
（自造样本→自定阈值→自检测→自评分）结构上同构，只是换了领域。

另外发现两处会直接暴露给面试官的硬伤：
- 骨架生成的 C# 里残留未渲染的 JS 拼接串：`"[TODO] 按《' + label + '手册》…"`（`GaoChuan`/`SoftWin.cs:49,61`）；
- README 标题在全品牌模式下印出 `undefined`。

## 四、真实强项（不为了批评而批评）

1. **虚拟控制器不是理想积分器**：含 1 µm 跟随误差、2 µm 噪声、固定随机种子、分段队列。
2. **`Check()` 失败即抛异常、退出码非 0**——是真断言，不是打 PASS 字。这正是我们实现期要的标准。
3. 单文件 HTML 自包含可双击（两段内联脚本，无外部引用），纯 JS 自实现 CRC32/ZIP。
4. C 级骨架 + TODO 清单的分级口径，是成熟的产品诚实性设计。

## 五、与本项目方向的裁决：不改变方向

| 维度 | 代码工厂（它） | 波形诊断（axiscope，我们） |
|---|---|---|
| 命中 JD | #2/#3/#8（写代码） | #9 + 任职要求 6（想问题、判故障） |
| 能力主张的锚点 | **无外部锚点**：SDK 签名只能靠手册，本项目拿不到手册 | 有：DaRUS 真实测量（T1-a）+ CWRU/Paderborn（T1-b）+ 文献阈值（T2） |
| 可证伪性 | "签名对不对"现场插卡才知道；面试被问"你核对过哪个"只能答"没有" | "判据是否成立"可用真实波形 + 文献阈值复核，且拒答是结构化输出 |
| 招聘方视角 | 会读手册的工程师很多；生成器谁都能搭（它自己就是证据） | 能把"偶发定位偏差"归因到三族并给出**证据行号**的人少 |
| 最大风险 | 看起来能跑，实则未验证（本项目最忌讳的姿态） | 自验证循环（已用 C5 三层证据 + 反事实自检压制） |

**结论：不换方向，不做第二个产品。** 代码工厂这条线在作品集里对我们只有**辅助价值**，
它证明了 JD 的另一半可以用 AI 替代，但那不是我们要展示的稀缺能力。

## 六、从它身上取走的三样东西

1. **适配层口径错误应成为一个正式归因目标**（KB0 §7 待并入）。它证明了"换卡不改业务代码"
   这个卖点的代价面：轴号基数（1-based/0-based）、脉冲当量单位口径（`PulsesPerUnit` 被当 UNITS 用）、
   DI/DO 有效电平取反——**这三类恰好是 `software_induced_pulse_eq_overwritten` 的上游机制**。
   我们的 agent 要能找到"适配层把单位悄悄换错"造成的定位偏差，这是主线上真实存在、
   且厂商调谐工具看不到的故障源。→ 落 KB3 R-22 的判据扩充。
2. **A/B/C 诚实分级的呈现方式**用在我们自己的跨厂商能力矩阵上（C5 §8 兜底方向、KB2 §4.9）：
   分级 + 就近标注 + 不可映射项清单。**不采纳**它把清单交给被检对象自身生成的做法——
   我们的清单来源必须是外部（手册页码/实测/文献），否则就是第三节那个循环。
3. **"验证性执行"作为交付门禁**：它用真实 `csc` 编译与真实退出码，这一点比 minimax 强。
   对应到我们：C5 的"无依据成功声明 = 0 次"必须是**机器可判定**的（loader 校验证据路径存在，
   规则只能引用 C2/C7 已登记路径），并像它一样让失败真的返回非 0。

## 七、三家横向定位（供最终叙事用）

| 家 | 切入 | 闭环形态 | 已暴露的失效模式 |
|---|---|---|---|
| minimax `mcopilot` | 日志取证 + 运动正算 + SDK 知识 + review | 6 个 agent，自造样本自评 | 自验证循环；6/9 检出数口径不符；只做完了正向预测半段 |
| GLM 系 代码工厂 | 分层代码生成 + 编译验证 | 真编译真运行，但跑的是虚拟控制器 | 签名无外部锚点；核对清单自我生成；"全品牌 PASS"实为 Virtual |
| 本项目 axiscope | 波形 → 特征 → 三族归因 → 数字先行建议 | 契约化 + 三层证据 + 拒答结构化 | 待 W+3d/W+7d 止损点检验（任务 #8、#12） |

三家共同点，也是本项目最该讲的一句话：**问题都不在"能不能生成"，在"谁来判定生成得对"。**
minimax 用自己的规则判自己，GLM 用照代码生成的清单判代码，
我们的答案是：**外部真值（T1）+ 文献阈值（T2）+ 结构化的"我不知道"（拒答与 not_evaluable）**。
