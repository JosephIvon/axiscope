## 一、一句话结论

**工程纪律是真的，且明显强于 GLM 那版；但它本轮的招牌话「逐条对着厂商官方手册原文核对」没有支撑。**
更糟的是，这句话恰好只出现在**两份面向外部的文档**里，而它自己的数据文件仍然诚实标着 `public-doc`。

## 二、核心项：证据等级判定（本轮最大问题）

| 检查 | 实测 |
|---|---|
| 仓库里是否有手册原文（PDF/扫描/摘录/头文件） | **无**。全库没有；`docs/` 只有那份《索取清单》 |
| 唯一的来源登记 | `knowledge/sdks/*.json` 的 `sources` 字段：**两条 CSDN 博客 URL** +「官方手册公开章节」的转述 |
| 它自己的定级字段 | 仍然是 `verified: "public-doc"` / `needs-manual-check`，**62 处**；README:299 明写"来自公开资料……仍建议用手册复核" |
| 措辞越级的地方 | ① `tests/test_mcopilot.py:485`「下面每一条都对着厂商**官方手册原文**核对过」；② 《索取清单》:95「已对照官方手册确认过了」 |

**判定：证据等级 = 二手网络转录。** `sources` 里没有任何一条能定位到手册页码或原文片段，
本机也无法追溯验证。所以"手册原文核对"这个声称**不成立**，它是 `public-doc` 的口头升格。

注意这构成**内部矛盾**而不是单纯吹牛：数据层的诚实定级和叙述层的更强措辞并存。
这正是最难被发现的失效模式——审计者读到"已对照官方手册"就会停止怀疑，
而那句话和仓库里最权威的证据标记恰好相反。

**对我自己的更正**：我上一条说《索取清单》是"本轮唯一能直接对外使用的产物"。
这个判断要打折——清单正文（9 项要什么/为什么/卡住哪段代码）依然可用，
但**附录那张「已确认项」表不能这么署名发出去**。发给 FAE 时说"已对照贵司手册确认"，
一旦对方翻出手册发现某条不符（例如 `HwPswitch2` 的模式参数口径），
损失的是整份清单的可信度。正确措辞是"我们按公开资料形成了下表，请贵司指出不符项"。

## 四、它自己没说的三处裂缝

1. **「调用即抛」只对了一半。** TODO 标记 23 处、`NotSupportedException` 确实存在于
   `ZMotion.Enable/MoveArc`、`Dmc.MoveLinear/MoveArc` 的代码路径上——
   但 `dmc` 的 `Enable`/`IsEnabled`/`GetState`/`SetCompareOutput`/`Home` 调的正是
   `needs-manual-check` 函数，**不抛异常、直接 P/Invoke**。
   即：标了"待核对"的地方，运行行为是"猜着跑"。安全故事在最关键的几个函数上有洞。
2. **`out/SimulatedMotionController.cs` 是含修复前两个 bug 的旧版**（diff 证实），
   README 目录树未列它。读者按目录树找不到、按目录翻到会拿到旧逻辑。
   （"删除工具按 reparse-point 拒绝删除"这句在本仓库内查不到对应代码，无法验证。）
3. **自创魔数写在成品代码路径上**，手册无据：
   `HwPswitch2` 多余 3 个比较点填 `1e9f`；Jog 硬编码 `MotionProfile(v, 1000.0, 5000.0)`；
   雷赛回零 `tAcc/tDec = 0.05`；SRAMP 250 ms / sPara 0.5 s 的 jerk→时间近似换算（注释自称近似，仍是自创公式）；
   `RegistModeFor` 的 0→3 / 1→14 / 2→18 / 3→20 映射（注释承认"推导自 DEMO 需手册确认"却**不抛异常直接执行**）；
   `GetStopReason` 把 5 视为正常，无出处。
   这与 GLM 版被打穿的"自创做法放在看起来像成品的代码里"是同一类问题，只是数量少得多。

## 六、对本项目的裁决

1. **方向不变。** 两家现在都聚在适配层（GLM 主动选它，minimax 三轮被它吸进去），
   而诊断这条线没有任何一家碰。这是作品集叙事里可以直接说的稀缺性证据。
2. **《索取清单》的 9 项结构直接复用**为 KB2 §4「跨厂商接入卡」的字段模板
   （要什么 / 为什么必须要 / 卡住哪段代码 / 已自行核对到哪一步），
   但附录那张"已确认项"表在我们这边**必须降级标注为 `public-doc`**。
3. **不采纳任何签名作为我们的事实来源**，只可在 KB2 里作为"二手转录，需手册核对"的线索，并署名。
4. **新增一条可机器判定的反吹牛规则**（落到 C3 硬性规则 14，见 KB0 §7 A-31）：
   报告叙述层的措辞强度不得超过数据层的证据等级字段；
   `audit` 块里每条结论带 `evidence_tier`，生成报告时若出现"已核对/已验证/现场确认"类措辞
   （★ 该条本轮记下的字段名后来被 A-54 统一为 **`source_tier`**，载体被 A-71 定为
   **`audit.tier_ledger[]`**；此处按当时的记录原样保留，读作历史记录而非当前口径。）
   而该结论 tier < T1，**loader 直接拒绝出报告**。
   本轮提供了一个真实、外部、可引用的失效案例来解释这条规则为什么必须存在——
   这比任何自造的"防幻觉设计说明"都有说服力。
5. 上一轮记入任务 #12 的**六个软件诱导缺陷形态**（DPOS 冒充反馈、`_unit` 双重换算差 1000 倍、
   IO 电平当错误码、PSO 比较点口径不明、回零后 MPOS 未同步、锁存源选错）**保留**。
   理由要写清楚：这些缺陷**形态**的成立不依赖手册哪一版是对的——
   它们是逻辑自洽的失败模式（例如 `_unit` 版已是 mm 再除当量必然差 1000 倍）。
   引用时标为"第三方实现审计中出现的缺陷形态"，不得标为"手册确认的错误"，也不得写成我们的发现。

## 七、第四轮状态更正（2026-10-20，A-89 触发）

本轮它**拿到了官方手册原文与官方 SDK 绑定源码**，并改成**机器抽取**而非手读：
`knowledge/sdks/official_api/{zmotion,leisai}.csv`（402 / 1391 个函数），对绑定层挂了三条断言。
**这两个文件我实数过行数**：`zmotion.csv` 402 行、`leisai.csv` 1391 行（去掉表头），与其声称逐字相符——
这是本轮唯一一处"外部工件 + 我方可复核"的证据，性质上高于它此前所有 `public-doc` 引用。
当场抓出三处"不报错、不写日志、真机才炸"的缺陷：
正运动 `ZAux_*` 实际在 `zaudll.dll` 而非 `zmotion.dll`（`EntryPointNotFoundException` 级别）、
`ZAux_Direct_SetAxisParam/GetAxisParam` 官方不存在、雷赛 `dmc_set_home_profile` 官方不存在（回零即崩）。
《索取清单》升为 **v3「手册已到手版」**：文件自陈 v1 是 9 项全量提问，v3 只剩 **4 类手册答不了的问题**
（形态 / 型号+接线盒 / IO 端子表+SERVO ON+CMP / SDK↔固件版本+位数，四类全部标"必答"）**+ 3 项建议**，
并新增「〇、我们已经收到的资料」表，逐条带版本——雷赛《DMC3000 系列卡用户使用手册》V2.0/20250710、
`LTDMC.cs/.dll` V2.5.7.23、正运动《ZMotion PC 函数库编程手册》**V2.1.4（714 页）** + `zauxdll2.h`/`Zmcaux.cs`/
`zauxdll.dll`。这张版本表就是 A-88 要求的 `verified_against = {manual_id, revision}` 载体——
它第一次让它的声称变成**可被证伪的**（FAE 只需指出某条不符）。

**本文 §二 的判定需要就地更正，但更正只对它成立**：
"仓库里是否有手册原文/头文件"这一行当时实测为**无**，因此本文把它的等级判为二手转录（= KB0 的 A-32）。
**A-32 这个结论对它已过期**——它现在有官方工件，且是抽取式使用，这是本轮质量跃升的真实原因。
但**对我们仓库仍然成立**：那些手册与绑定不在我们的 `docs/evidence/` 或 `data/raw/` 里，
所以它的抽取结果对我们是 `external_reference = public-doc`、`verified_by = third_party_report`，
**不得计入我们的 `已核对 k`**（A-89 核对主体不可转借；参 C4 的 A-89 收窄条）。
